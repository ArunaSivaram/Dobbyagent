Why this exists

Important dates arrive buried in WhatsApp groups, email chains, forwarded school circulars, and group newsletters. Most people retype them into a calendar, or they don't, and something gets missed. The work itself is small but it's constant, and the cost of a single miss, a forgotten appointment, an unpaid fee, a deadline that slipped, is high enough to keep the problem worth solving.

A fixed form can't do this, because the inputs are too varied. Messages use relative dates like "next Friday", bundle several events into one block of text, mix deadlines with chit chat, and often restate events already on the calendar. An LLM handles the reading. Tools let it check the calendar before writing to it. The result is a small, private, reversible agent that removes a recurring micro chore without putting anyone's data in motion by accident.

Who it's for

Primary
The person doing the organising

Lives in WhatsApp and email, drops dates into a calendar by habit, forgets some of them anyway. Wants to paste once and trust the result.

Secondary
Family or household members

Share the same household schedule. Either get their own Dobby account, or read events off the shared family calendar the primary user chose to write to.

Beta user
Invited by the owner

Needs simple onboarding, a clear privacy note, an easy undo for anything Dobby got wrong.

Scope

In scope for v1
  • Text messages pasted or forwarded into Telegram.
  • Photos and PDFs of circulars (screenshots, scans, school handouts).
  • Event, deadline, and multi-day extraction with relative dates resolved.
  • Duplicate check before writing to Google Calendar.
  • Reminders at 7 days, 2 days, and on the day, at the user's chosen time.
  • Per-user token and cost tracking with a monthly budget.
  • Invite-only multi-user access, each user linking their own calendar.
Out of scope for v1
  • Editing or rescheduling events by chat (v2 candidate).
  • Recurring events as a series. v1 creates the first occurrence and says so.
  • A WhatsApp bot for input (needs Meta Business setup and paid templates).
  • Calendars other than Google (Outlook, iCloud).
  • Public sign up. Google caps unverified apps at 100 users.

Autonomy and guardrails

Dobby acts on its own only for additive, reversible actions. It creates events in the user's own calendar and messages that one user. It never edits or deletes anything it didn't create, and it never contacts anyone else. Every write is undoable with /undo. A message that would create more than ten events switches to confirm mode.

How it works

Dobby is a ReAct loop. The LLM reasons about the message, asks for a tool, the loop runs the tool, hands the result back, and the loop repeats until the model says it's done. The loop never imports a provider SDK. Both the LLM side and the calendar side sit behind small interfaces, which is why the same agent code runs against Claude in production and against a fake calendar in evals, without a line of change.

The Telegram bot is a thin adapter in front of the loop. It polls Telegram for messages, checks the sender against an allowlist, and dispatches on content: free text runs the full agent loop, a photo or small PDF is transcribed once and then runs the same loop, /upcoming and /undo go straight to the calendar. The agent itself is unaware Telegram exists — python -m dobby "…" and the bot both call run_agent() with the same arguments, and files feed in as the resulting transcript.

Evals and release gate

Every model ships only when it clears every row in the scorecard below. The golden set has thirty text cases across ten categories, covering single events, multi event messages, relative dates, deadlines, multi day events, chit chat, duplicates, ambiguous phrasing, prompt injection, and messy formatting. Each case runs three times against a fresh fake calendar. The mean across runs is scored against a fixed threshold. Code graders only, no LLM judge yet.

Cost comparison

Dobby runs cheap. Every Claude call is logged with its exact token counts, costed from the published price table, and summed into per run, per user, and per month totals. The monthly budget per user defaults to $0.50. The sections below show the headline numbers and the full math.

How we calculate the cost per message

Every call to Claude returns four token counts in response.usage: input tokens, output tokens, cache read tokens, and cache write tokens. Each is multiplied by the per million token price for its model, then summed and divided by one million.

cost = (0.10 * input + 0.50 * output + 0.01 * cache_read + 0.125 * cache_write) / 1_000_000

A text run (one message) has several calls because of the tool loop, so the run cost is the sum of its calls. A photo or PDF run adds one upfront vision call (see the next section), then the same tool loop. Ollama runs are local, so cost is always $0.

Transcription cost for photos and PDFs

A photo or PDF adds one Claude vision call before the agent loop. The image or document bytes are counted as input tokens using the same per million price; the output is the transcript itself, typically 200–500 tokens of plain prose. Images are capped at 5 MB, PDFs at 10 MB and 5 pages, so the bytes staying small keeps the cost bounded.

Monthly budget math

At the measured $0.0005 per text message on Haiku, a user sending sixty messages in a month costs about $0.03. Default budget is $0.50, which leaves room for photos and PDFs — measured at 2–3× text cost (see Transcription cost for photos and PDFs above).

Before each run, the service sums this month's cost_usd for the user. At 80 percent of budget, a one line warning is appended to the reply. At 100 percent, Dobby pauses. No model call fires, and a polite message goes back.

A hard monthly spend limit is also set in the Anthropic Console as a backstop above the per user guard.

Why pay for Haiku when Qwen is free?

Qwen3:8b running locally has two things going for it: zero per message cost, and nothing leaves the user's machine. Haiku 4.5 has two things going for it: strong tool use and consistent instruction following on long system prompts.

The comparison in the scorecard above decides this empirically. If Qwen3:8b clears every threshold, we can offer a "no cloud" mode without a feature trade. If not, the gap on each metric is the shopping list of what to fix (prompt, bigger open model, or hosted open model).

    Risks and open questions
